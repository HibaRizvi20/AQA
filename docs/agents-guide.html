How it fits together

Hand AQA a scope link (a tracker epic/story or a plain feature spec) and it drives it toward a reviewed, passing test suite: cases published, bugs raised with evidence, coverage recorded — with a human at five gates, not an unattended robot.

  • Intent vs truth. Docs and designs drift; the live app is the only source of truth — every selector and behaviour is verified against the running app.
  • Gates + dry-run. Nothing external is sent without the matching human gate and an explicit confirm. A 2xx is never "success" — the inner result is asserted.
  • Pickable tests. Every scenario is auto-tagged by @area and @type, so any subset runs on demand.
  • Never fake green. If something can't be verified (a feature isn't built), the pipeline says so.

Pipeline agents (the gated authoring flow)

1 · Scope Analyst 01 → CP1

Turns a scope link into a classified, testable scope with a confidence rating. Read-only.

How: traverses the link, classifies each item as in-scope / deferred / out-of-scope, groups by area, and emits a confidence that forces early review when low.

Does NOT write tests or resolve intent-vs-app disagreements (flags them for CP1).

2 · Test Architect 02 → CP1

Turns the scope into a plan: objectives, the positive/negative/edge split, target modules, risks, and a pilot.

How: routes each item to a track (UI/API/perf), one testable objective per behaviour, names real modules.

3 · Case Designer 03 → CP2

Writes each objective as a stakeholder-readable Gherkin scenario — and auto-stamps @area + @type tags.

How: Given/When/Then in business language, right granularity, grounded in the real app, co-located with its step file.

4 · Tracker Publisher 3b

Publishes the approved scenarios as issue-tracker test cases — dry-run first, nothing sent until confirmed.

5 · Test Generator 04 → CP3

Turns Gherkin into runnable Playwright step definitions, reusing shared page objects. Live-verifies every selector; a dated skip if an element is absent.

Does NOT edit shared page objects (freeze) or self-heal.

6 · Triage / Self-Healer 06

Classifies each failure (known-flaky / test-defect / product-bug), fixes test defects in ≤3 cycles, raises evidenced bugs for the rest. Never fakes green.

7 · Reviewer 08 → CP5

Checklist review vs conventions (tracker key, tags present, page-object freeze, no bare 2xx, self-contained, selectors verified) → a dry-run PR comment. Comments, doesn't merge.

8 · KB Curator 09

Maintains the git-versioned Feature Registry — intent, truth (routes/APIs), our tests, freshness stamp, coverage delta.

Async-track agents (non-blocking)

9 · Performance & Logs async

Pulls runtimes + logs, summarises where time goes; raises a bug only on a clear budget breach. Report-only.

10 · Drift Detector async

On an app change, re-verifies Feature-Registry anchors against the live app and flags drift so tests don't silently rot.

11 · Design-Parity Analyst async

Compares a design prototype vs the built app and files design-team tickets (not product bugs) for meaningful deviations.

12 · Eval Analyst async

Scores an AI assistant against a golden dataset — LLM-as-judge (correctness/faithfulness) + deterministic checks (tools, trace health). Report-only.

End-to-end flow

1
Scope Analyst → Test Architect
scope classified, plan built.
⏸ CP1 — human reviews scope + plan
2
Case Designer
Gherkin written + auto-tagged.
⏸ CP2 — human reviews the cases
3
Tracker Publisher (dry-run) → Test Generator
step defs written, selectors live-verified.
⏸ CP3 — human reviews the generated code
4
Targeted Run → Triage/Self-Heal
touched specs run; failures triaged/fixed.
⏸ CP4 — human triages failures
5
Regression → Reviewer
whole suite green; checklist review.
⏸ CP5 — human approves the merge
6
Finalise + KB Curator
Feature Registry updated; coverage recorded.

The async tracks (Performance, Drift, Design-Parity, Eval) run alongside and never block the merge.

Use separately, or as skills

Every agent runs on its own, and shared capabilities are packaged as skills. Five ways to use the framework:

node pipeline/orchestrator.mjs PROJ-101            # the whole gated pipeline
node pipeline/orchestrator.mjs PROJ-101 --approve CP1
# — invoke a single agent (just scope, just eval, just drift)…
# — use a skill directly (verify a selector, publish a ticket, pull perf)…
BDD_TAGS="@area:checkout and @type:negative" npm run test:bdd   # pick tests by tag
npx playwright test --grep "@type:edge"

Rule of thumb: the whole pipeline for a full feature; one agent for one step; one skill for one small task. Everything external stays dry-run until a human says "send it", and the live app — never the doc — is the source of truth.
